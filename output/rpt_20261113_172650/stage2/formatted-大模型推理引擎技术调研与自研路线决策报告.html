一、摘要

本报告基于九轮 GitHub 深度调研，覆盖 60 余个推理引擎与相关基础设施项目，回答一个问题：在 2026 年，一个没有大厂资源的团队，自研大模型推理引擎的正确切入点是哪里？

核心结论是：不自研通用推理引擎，先做 RL 训练与推理引擎之间的"数据契约适配层"。

理由有三。其一，通用引擎已被 vLLM（96,857★）、SGLang（38,804★）与 TensorRT-LLM 的生态壁垒锁死，自研无差异。其二，Kernel 层的极限已被 DeepSeek 的 DeepGEMM（BF16 达硬件极限 99.8%）探明，难以超越。其三，推理与 RL 训练之间至今存在一条字段级不统一的缝隙——同一份 MoE 路由数据，vLLM、SGLang、Megatron 用了三种不同 dtype 与三种不同传输格式，边界约定互不一致。这条缝隙有真实需求、有可对齐的事实标准、且工程量可控。

本报告给出四阶段实施路线、50 行代码即可验证的最小闭环，以及明确的验收标准。

二、调研方法与范围

三、市场格局

3.1 三层分化

2026 年的推理基础设施已经分化为三层，任何新进入者都必须先明确自己属于哪一层：

层次代表项目定位
引擎层vLLM、SGLang、TensorRT-LLM承载模型权重、调度请求、管理 KV cache
编排层NVIDIA Dynamo 1.0、llm-d（CNCF Sandbox）在引擎之上做 PD 分离决策、多副本调度
KV 层Mooncake、LMCache、NIXL把 KV cache 从引擎解耦成独立基础设施

关键含义：编排层与 KV 层都不自己写引擎，而是在引擎之上/之下做差异化。这是"不重造引擎也能生存"的实证。

3.2 主流引擎对比

3.3 两个格局信号

其一，HuggingFace TGI 已归档（archived: true，最后提交 2026-03-21），HF 自家 Inference Endpoints 转向 vLLM。曾经的四强之一退场，说明这个领域没有"稳定胜利者"。

其二，DeepSeek 的 FlashMLA 放弃 Hopper 支持，只保留 Blackwell 与 Ascend 950。前沿实验室已不再把上一代 NVIDIA 芯片当作优化目标——平台押注的窗口正在移动。

五、可复用零件层

造引擎已经不需要从零写。2026 年的现实是"组装 + 在一层做差异"：

结论：自研的应该只有调度器与状态管理——那是唯一能形成差异的地方。

六、纵向范本：DeepSeek 昇腾六件套

2026-09-30，DeepSeek 开源了整套昇腾软件栈（MIT），六个组件，是"自研引擎"最完整的范本：

组件关键数据

DeepEP-AscendEP8 下 dispatch 373-375 GB/s，约 90-95% 物理带宽上限

配套硬件：昇腾 950DT（144GB 自研内存、4TB/s、1 PFLOPS FP8）；SuperPoD Flex（128 卡单层 3.2Tbps，可扩 256K 卡）。

重要边界（已验证事实）：DeepEP-Ascend 的带宽数据来自 DeepSeek 提供的 PoC HDK（非公开发售版本），其 README 明确提示早期 PoC 硬件可能更低，官方基线应以华为商用品为准。

七、被忽略的战场：RL 与推理的接口（本报告重点）

7.1 三个独立偏差源

RL（强化学习）训练不稳定，有三个互相独立的来源，各有一个对应机制，缺一不可：

偏差源表现修法
路由偏差MoE 推理与训练为同一 token 选不同专家R3（Router Replay）
动作空间偏差top-p 截断使采样分布 ≠ 训练全词表sampling mask
打分偏差推理与训练 logprob 因 kernel/精度/策略滞后不相等score centering

社区最常见的错误是只修一个就宣布解决，另外两个仍在悄悄污染梯度。

7.2 R3 实现现状

实现方状态
vLLM--enable-return-routed-experts 已上线，返回 routed_experts（[gen_len, layers, top_k]，dtype uint8/uint16）与 prompt_routed_experts
NeMo RL v0.7PR #2590 实现 R3（vLLM 路线），约 4059 行，支持 Sync/Async RL
阿里 ROLL也实现 R3，但走 SGLang 路线，明确不支持 vLLM rollout
Megatron-LMPR #79 给出最细边界处理，未合入主干
论文R3 = arXiv:2606.02437

7.3 字段级分歧——协议不统一的最硬证据

同一份语义数据，三种 dtype、三种传输格式：

实现dtype体积（同一数据）
vLLM 官方uint8（≤256 专家）/ uint161×
部分 fork 文档int162×
Miles 实测int322-4×

32K token、60 层、top_k=8 的一条 rollout 轨迹，路由数据就约 60MB（int32）。统一 dtype 后同样数据可降到 15MB。

7.4 四类静默失败（不报错，只是数据不对）

这是实现协议时最危险、最该先处理的坑：

其一，CUDA graph 与 NCCL 死锁：只有 rank 0 持有 device buffer 会导致各 rank 代码路径不同、图结构不对称，collective 中偶发 hang。解法是所有 rank 都分配真实 buffer。

其二，被抢占的请求静默丢路由：host cache 中已累积的路由被丢弃且不发出，消费方只看到 None，无任何信号。

其三，异步调度下 EOS 静默丢路由：stop 判断读到 placeholder -1。

其四，流式不可用 / Rust HTTP 前端永不返回该字段。

7.5 成本真相

指标数值
R3 吞吐开销约 -2%（ISL/OSL=1024）
R3 显存开销约 14MB/GPU（40 层/8192 token/top-22）
R3 精度影响零差异（GSM8K pass@1 完全一致）
传输体积约 60MB/条轨迹（32K token）
sampling mask 吞吐代价num_sampler_logprobs=8 且单 API server 时减半；加 8 个 API server 后 <3%

关键认知：R3 的那 2% 吞吐不是成本，60MB 传输才是；mask 的成本不在显存，而在 CPU 序列化。

7.6 sampling mask 的配对要求

--return-sampling-mask 必须与 --logprobs-mode processed_logprobs 同时使用。只开 mask 不改 logprobs 模式，返回的 logprob 仍在全词表归一化，而 mask 定义的是核内支撑集——分子分母不在同一空间，比率照样有偏。训练侧还需：

keep = torch.zeros(vocab_size, dtype=torch.bool); keep[mask_ids] = True
log_prob = log_softmax(logits.masked_fill(~keep, -inf))[sampled_token_id]

八、机会评估

8.1 已被填满的坑（不要碰）

PagedAttention 式 KV 管理、连续批处理、OpenAI 兼容协议、基础量化（AWQ/GPTQ/FP8）、单点投机解码——这些是入场券，不是差异点。

8.2 三条备选路线的取舍（判断）

路线为什么不选
约束型引擎（国产芯片/端侧）需算子功底与厂商关系，Chitu 已占位
调度层创新（Agent DAG）工程量小但缺场景验证，且尚无明确需求方
做零件（kernel/量化）DeepGEMM 的 99.8% 无法超越

8.3 选中的缝隙

跨引擎的 RL 数据契约适配层。理由：需求真实（16 个开源 RL 库各自造轮子）、有可对齐的事实标准（vLLM 的字段）、工程量可控、且两派已分叉（NeMo RL 走 vLLM，ROLL 走 SGLang 且互不兼容）。

九、最终方案

9.1 决策：先实现协议，不定义协议

理由：定义协议需要生态号召力，实现协议可在实践中积累话语权；且 vLLM 的 routed_experts / SamplingMask 已是事实标准，与它对齐的成本远低于另起一套。

9.2 定位

跨引擎的 RL 数据契约适配层——统一 routed_experts 与 sampling_mask 的 dtype、形状、边界约定，并提供一致性校验。

9.3 四阶段实施路线

阶段周期目标
阶段一约 1 周在 vLLM 上跑通 R3 + sampling mask 的最小验证
阶段二1-2 周dtype 归一化 + 三类边界处理（末 token 无路由 / 中止为 null / 不可映射 -1 哨兵）
阶段三2-3 周vLLM / SGLang 双引擎适配
阶段四持续一致性校验工具与指标

9.4 最小验证方案（50 行代码可验证）

第一步，启动服务并保证批不变性：vllm serve <moe-model> --enable-return-routed-experts，同时设环境变量 VLLM_BATCH_INVARIANT=1。

第二步，取一条 routed_experts，断言 shape[0] == prompt_len + gen_len - 1（末 token 无路由）。

第三步，训练侧把同一批 token 的专家强制成该索引。

第四步，对比 logprob 差异：归零则契约成立；不归零则已定位到第一个要修的点。

9.5 验收标准与指标

logprob 差异归零或低于阈值；unmappable_frac 可观测（不可映射 token 比例）；抢占场景能被显式检测，而非静默丢数据。

9.6 风险与边界

vLLM 字段仍在演进（weight_versions 仅存在于 fork），上游合并状态不确定；PD 分离与 R3 目前不兼容（Nixl/Mooncake 等 KV connector 被拒）；若上游统一协议，适配层价值下降——应对：把适配层做成可被上游吸收的形态。

十、结论与下一步

九轮调研把问题收敛到一句话：在约束条件里做引擎，比在无约束条件里做引擎容易十倍；而当前最真实的约束条件是"推理与训练之间没有统一的契约"。

未来 30 天的三个动作：

1. 用 50 行最小验证脚本在 vLLM 上跑通 R3，确认 logprob 差异能否归零。

2. 写 dtype 归一化层，覆盖 uint8/uint16/int32 三种输入。

3. 处理三类静默失败，重点是被抢占请求的显式检测。
